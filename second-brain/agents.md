# agents.md — 操作手册

> **这个文件就是整套系统的"源代码"。** 改行为 = 改这个文件，不需要动代码。
> 原始设计来自 Andrej Karpathy 的 LLM Wiki 概念：让 LLM 增量维护一份常驻的、
> 互相链接的 markdown wiki，而不是每次提问都去原始文档里现查。
>
> 这份文件就是 Karpathy 说的 **the schema** —— 它才是让 LLM 成为一个
> "守规矩的 wiki 维护者"而不是通用聊天机器人的关键。

- **库根目录**：就是本文件所在的文件夹。让你的 agent 直接在这个库里工作即可
- **前端**：就是这些 markdown 文件本身。装了 Obsidian 可以直接「打开文件夹作为库」
  （可选，不是必须）

---

## 1. 给人看的使用说明

直接用大白话跟你的 agent 说就行：

| 你想要的 | 就说什么 |
|---|---|
| 存一篇网页 / 视频进来 | 「把 <URL> 存进第二大脑」 |
| 把新素材加工成 wiki | 「处理 raw 里没处理的文件」 |
| 问知识 | 「问一下第二大脑：<问题>」 |
| 给库做体检 | 「给这个库做一次 lint」 |
| 改系统行为 | 直接改这个文件（也可以让 agent 改） |

---

## 2. 目录结构

```
second-brain/
├── raw/                    ← 原始素材，不可变。原封不动放这里
│   └── assets/             ← 本地附件（图片等）
├── wiki/                   ← AI 生成的 markdown（只由 AI 写，你只读）
│   ├── sources/            ← 每个来源一个页面（它是什么、讲了什么）
│   ├── concepts/           ← 概念 / 主题
│   ├── entities/           ← 人物、公司、组织
│   ├── tools/              ← 工具、产品
│   └── synthesis/          ← 综述、对比
├── index.md                ← 全库目录（内容导向）
├── log.md                  ← 操作日志（时间导向）
└── agents.md               ← 本文件（schema）
```

**三层各归谁管：**

| 层 | 是什么 | 谁写 |
|---|---|---|
| **Raw sources** | 策展过的来源文件，**不可变**，事实的唯一来源 | 你 |
| **The wiki** | 摘要、实体页、概念页、对比、综述 | **LLM 完全拥有**，你只读 |
| **The schema** | 本文件 —— 结构、约定、工作流 | 你和 LLM 共同演进 |

## 3. Operations: ingest（加工新素材）

当用户添加了一个来源、并要求处理它时，按顺序做这五步：

1. **read the source from raw** —— 读 `raw/` 下的源文件
2. **create or update wiki pages** —— 在 `wiki/` 下创建或更新对应页面
   （先在 `wiki/sources/` 里给它建一个来源页）
3. **update relevant pages** —— 更新受影响的实体 / 概念 / 工具 / 综述 / 对比页
4. **update index.md** —— 把新页面登记进目录
5. **append an entry to log.md** —— 追加一条日志。**格式必须是**
   `## [YYYY-MM-DD] ingest | 标题`，下面列新建 / 更新了哪些页面。
   统一前缀是为了能用 `grep "^## \[" log.md | tail -5` 取最近几条

**判断"加工过没有"的依据**：看 `wiki/sources/` 里有没有对应的来源页。
**`raw/` 里的源文件永远不动、不删、不移动** —— 它是不可变的事实来源。

### 加工时的写作要求

- **忠实于原文**，不臆造事实。来源没说的不写
- 每个 wiki 页面开头放 front matter：
  ```yaml
  ---
  type: source | concept | entity | tool | synthesis
  title: ...
  sources: ["对应来源页的标题"]
  updated: YYYY-MM-DD
  ---
  ```
- **必须交叉链接**：
  - 新生成 / 更新过的 wiki 页面 → 链接到它的来源页（**不要留孤儿页**）
  - 概念页里提到的人物、工具、公司，用 `[[wiki/entities/xxx]]` 这种相对路径链上
- 页面之间用相对路径互链，Obsidian 的 graph view 才有东西可看

## 4. Operations: query（回答问题）

用户提问时：

1. **先查 `index.md`** —— 看库里有什么
2. 去读相关的 wiki 页面（而不是凭 LLM 自己的通用知识回答）
3. 回答时**指明依据来自哪个页面**
4. **回写**：如果回答里有可复用的知识，把它补成新的 wiki 页面，并
   - 更新 `index.md`
   - 在 `log.md` 里记一笔
   - 新页面链回它的来源

> 这就是这套系统跟普通笔记软件的根本区别：**提问本身也在生产知识。**

---

## 5. Operations: lint（给库做体检）

用户说「lint」「体检」时，扫一遍全库，找这些东西：

- 页面之间的矛盾说法
- 被新来源推翻的过时结论
- **孤儿页** —— 没有任何页面链接它的页面
- 被反复提到、却没有自己页面的重要概念
- 缺失的交叉引用
- 可以用一次搜索补上的数据缺口
- 值得调研的新问题 / 值得找的新来源

输出一份清单，标出每一项在哪几个页面里，然后问用户要不要修。

## 6. 未来的扩展

这套东西是活的，随你改。想加东西时，**在库里新建一个文件夹，然后在这个文件里写清它的规则**：

- 想记人 → 加一个 `crm/`
- 想记日记 → 加一个 `journal/`
- 需要远端备份 → 给这个库加个 git remote
- 库大到 `index.md` 读一遍也费劲了 → 加一层本地搜索引擎
  （Karpathy 点名的是 [`qmd`](https://github.com/tobi/qmd)，
  在 wiki 之上加检索，不替换 wiki）

> **改这个文件 = 改整个系统。** 你描述得越精确，它才越像你想的那样。
