# LLM Wiki

**一句话定义**：不让 LLM 在提问时去原始文档里现查（RAG），而是让它
**增量地维护一份常驻的、互相链接的 markdown wiki**，知识**编译一次、之后只做维护**。

## 它跟 RAG 的根本分歧

| | RAG | LLM Wiki |
|---|---|---|
| 知识存在哪 | 原始文档的切片里 | 一份被 LLM 加工过的 wiki 里 |
| 什么时候加工 | 提问时现取现拼 | 摄入时就整合进去 |
| 有没有积累 | **没有** —— 每次从零重新发现 | **有** —— 每加一个来源、每问一个问题都更厚 |
| 矛盾怎么办 | 不知道，每次看你运气 | **已经被标出来了** |
| 综合结论 | 每次重新推导 | 已经反映了你读过的全部东西 |

**关键差异：wiki 是一个常驻的、会复利增长的产物（persistent, compounding artifact）。**

## 三层结构

| 层 | 内容 | 谁写 |
|---|---|---|
| **Raw sources** | 策展过的来源文档，**不可变**，是事实的唯一来源 | 你 |
| **The wiki** | 摘要、实体页、概念页、对比、总览、综述 | **LLM 完全拥有**，你只读 |
| **The schema** | `AGENTS.md` / `CLAUDE.md` —— 结构、约定、工作流 | 你和 LLM 共同演进 |

> **The schema 是让 LLM 成为"守规矩的维护者"而不是通用聊天机器人的关键。**
> 它是一个**关键的配置文件**，也是你和 LLM 一起慢慢演进的东西。

## 三个操作

- **Ingest** —— 读源文件 → 写摘要页 → 更新索引 → 更新受影响的实体/概念页 → 追加日志。
  **一个来源可能触及 10~15 个 wiki 页面。**
- **Query** —— 先读索引 → 找相关页 → 带引用地综合出答案。
  **好答案要归档回 wiki 成为新页面**，不该消失在聊天记录里。
- **Lint** —— 定期体检：页面矛盾、过时说法、孤儿页、缺失的概念页、缺的交叉引用、数据缺口。

## 两个特殊文件

- **`index.md`（内容导向）** —— 全库目录，每条带链接 + 一句话摘要，按类别组织。
  **回答问题时先读它。** 在约 100 个来源、数百个页面的规模下够用，**不需要向量检索基础设施**。
- **`log.md`（时间导向）** —— 追加式记录。每条统一前缀（`## [日期] ingest | 标题`）的话，
  就能用 `grep "^## \[" log.md | tail -5` 取最近几条。

## 为什么这套能成立

维护知识库真正累的**不是读、不是想，是记账**：更新交叉引用、让摘要保鲜、记录哪些旧说法被推翻、
在几十个页面之间维持一致。**人类放弃 wiki，是因为维护成本涨得比价值快。**

LLM 不会无聊、不会漏掉一个交叉引用、一轮能改 15 个文件 ——
**wiki 之所以能被维护住，是因为维护成本趋近于零。**

**分工**：人负责找料、探索、提好问题；LLM 负责其余全部。Karpathy 自己的类比是
「**Obsidian 是 IDE，LLM 是程序员，wiki 是代码库**」。

## 思想前身

Vannevar Bush 1945 年的 **Memex** —— 一个私人的、策展过的知识库，文档之间有"联想路径"。
Bush 的构想其实比万维网更接近这个东西：私密、主动策展、
**文档之间的连接和文档本身一样有价值**。
**他没解决的那部分，是谁来做维护。LLM 把这个接住了。**
