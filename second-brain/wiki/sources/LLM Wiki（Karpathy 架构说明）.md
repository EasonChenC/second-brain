# LLM Wiki（Karpathy 架构说明）

**原始素材**：`raw/LLM-Wiki.md`｜类型：文章｜发布：2026-04-04

> 这是一份"点子文件（idea file）"，作者明确说它是给人复制粘贴给自己的 LLM Agent 用的
> （举例写的是 OpenAI Codex、Claude Code、OpenCode / Pi）。它只讲高层思路，
> 具体实现由你的 agent 跟你一起长出来。

## 核心主张

大多数人用 LLM 处理文档的方式是 **RAG**：上传一堆文件，提问时检索相关片段，生成答案。
能work，但**LLM 每问一次都要从零重新发现知识 —— 没有积累**。一个需要综合五份文档的微妙问题，
每次都得重新拼一遍碎片。NotebookLM、ChatGPT 的文件上传、大多数 RAG 系统都是这样。

Karpathy 提的是另一条路：不是每次查询时才去原始文档里检索，而是让 LLM
**增量地构建并维护一份常驻的 wiki** —— 一份位于你和原始素材之间、结构化、互相链接的 markdown 集合。

新增一个来源时，LLM 不只是把它索引起来等着检索。它会读进去、抽出关键信息、
**整合进已有的 wiki**：更新实体页、修订主题摘要、标注新数据在哪里跟旧说法冲突、
强化或挑战正在形成的综述。

一句话概括：**wiki 是一个常驻的、会复利增长的产物（persistent, compounding artifact）。**
交叉引用已经在那儿了，矛盾已经被标出来了，综述已经反映了你读过的全部东西。

**分工**：你负责找料、探索、提出好问题。LLM 负责其余全部 —— 摘要、交叉引用、归档、记账。
他自己是这么描述的：

> **Obsidian 是 IDE，LLM 是程序员，wiki 是代码库。**

## 三层架构

| 层 | 是什么 | 谁拥有 |
|---|---|---|
| **Raw sources** | 策展过的来源文档（文章、论文、图片、数据）。**不可变**，LLM 只读不改。事实的唯一来源 | 你 |
| **The wiki** | LLM 生成的 markdown 目录：摘要、实体页、概念页、对比、总览、综述 | LLM 完全拥有，你只读 |
| **The schema** | 一份文档（如 Claude Code 的 `CLAUDE.md`、Codex 的 `AGENTS.md`），告诉 LLM wiki 怎么组织、有哪些约定、ingest / 查询 / 维护时走什么流程 | 你和 LLM 共同演进 |

**schema 是关键的配置文件**——它才是让 LLM 成为一个"守规矩的 wiki 维护者"而不是通用聊天机器人的东西。

## 三个操作

- **Ingest（摄入）**：把新来源丢进 raw，让 LLM 处理。参考流程：读源文件 → 跟你讨论关键要点 →
  写摘要页 → 更新索引 → 更新受影响的实体页和概念页 → 追加一条日志。
  **一个来源可能触及 10~15 个 wiki 页面。** 他本人偏好一次一个、全程参与。
- **Query（查询）**：针对 wiki 提问。LLM 找相关页面、读、带引用地综合出答案。
  答案形式可以多样（markdown 页、对比表、Marp 幻灯片、matplotlib 图表、canvas）。
  关键洞察：**好的答案应该被归档回 wiki 成为新页面** —— 一个对比、一份分析、一个你发现的关联，
  不该消失在聊天记录里。
- **Lint（体检）**：定期让 LLM 给 wiki 做健康检查 —— 页面之间的矛盾、被新来源推翻的过时说法、
  没有入链的孤儿页、被反复提到却没有自己页面的重要概念、缺失的交叉引用、可以用搜索补上的数据缺口。

## 两个特殊文件

- **`index.md` 是内容导向的**：wiki 里一切东西的目录，每条带链接 + 一句话摘要 + 可选元数据，
  按类别组织。每次 ingest 都更新。回答问题时**先读索引**再深入具体页面。
  作者说这个在中等规模（约 100 个来源、数百个页面）下"出奇地好用"，**不需要向量检索那一套基础设施**。
- **`log.md` 是时间导向的**：追加式的操作记录（ingest / query / lint）。
  技巧：每条以统一前缀开头（如 `## [2026-04-02] ingest | 标题`），
  日志就能用最简单的 unix 工具解析 —— `grep "^## \[" log.md | tail -5` 就取最近 5 条。

## 可选工具与技巧

- **Obsidian Web Clipper** —— 浏览器插件，网页转 markdown，快速把来源塞进 raw
- **图片本地化** —— Obsidian 设置里把附件目录指到 `raw/assets/`，再给"下载当前文件的附件"绑个快捷键
- **Obsidian graph view** —— 看 wiki 形状最好的方式：什么连着谁、哪些是枢纽、哪些是孤儿
- **Marp** —— markdown 做幻灯片；**Dataview** —— 用 frontmatter 跑查询生成动态表格
- **CLI 工具**：规模大了可以上 [`qmd`](https://github.com/tobi/qmd)（本地 markdown 搜索引擎，
  BM25 + 向量混合检索 + LLM 重排，同时提供 CLI 和 MCP server）
- **wiki 本身就是一堆 markdown 的 git 仓库** —— 版本历史、分支、协作全都免费得到

## 为什么这套能成立

维护知识库真正累的部分**不是读、也不是想，而是记账**：更新交叉引用、让摘要保持新鲜、
记录新数据在哪推翻了旧说法、在几十个页面之间维持一致性。

**人类放弃 wiki，是因为维护成本增长得比价值快。** LLM 不会无聊、不会忘记更新一个交叉引用，
而且一轮能改 15 个文件。wiki 之所以能被维护住，是因为**维护成本趋近于零**。

思想上可追溯到 Vannevar Bush 1945 年的 **Memex** —— 一个私人的、策展过的知识库，
文档之间有"联想路径"。Bush 的构想其实更接近这个东西而不是它后来变成的万维网：
私密、主动策展、**文档之间的连接和文档本身一样有价值**。

**他没解决的那部分，是谁来做维护。LLM 把这个接住了。**
