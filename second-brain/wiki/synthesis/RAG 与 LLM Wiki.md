# RAG 与 LLM Wiki

这两条路都在解决同一个问题：**让 LLM 用上它训练数据里没有的知识。**
但它们的假设完全不同。

## 正面对比

| 维度 | RAG | LLM Wiki |
|---|---|---|
| 知识存在哪 | 原始文档 + 向量索引 | 一份被 LLM 加工维护的 markdown wiki |
| 加工发生在什么时候 | **提问时**（检索 → 现拼） | **摄入时**（读进去 → 整合） |
| 有没有积累 | **没有** —— 每次从零重新发现 | **有** —— 复利式增长 |
| 需要综合五份文档的问题 | 每次都要重新找、重新拼 | 综合早就写在那儿了 |
| 矛盾怎么处理 | 不知道，看运气 | 摄入时就标注出来了 |
| 基础设施 | 向量库 / embedding / 检索调优 | **一批 markdown 文件** + 一个索引文件 |
| 规模化 | 天然可扩 | 作者实测约 100 来源 / 数百页内，索引文件够用；再大才需要搜索引擎 |

## Karpathy 的原话

> 大多数人的体验看起来像 RAG：上传一堆文件，LLM 在提问时检索相关片段，生成答案。
> 能work，但 **LLM 每问一次都在从零重新发现知识。没有积累。**
> 一个需要综合五份文档的微妙问题，每次都得重新拼碎片。什么都没被建立起来。
> NotebookLM、ChatGPT 文件上传、大多数 RAG 系统都是这样。

## 谁才是"对"的

**不是二选一**，它们适合的场景不同：

- **一次性的大文档问答**（读完就完事）→ RAG 够了
- **长期积累、要反复回访、要形成判断的领域**（个人知识库、研究、竞品分析、读书）→ LLM Wiki 更合适
- 规模真的很大（远超数百页）时，**两者可以叠加** —— Karpathy 提到的
  [`qmd`](https://github.com/tobi/qmd)（BM25 + 向量混合检索 + LLM 重排，本地跑）
  就是在 wiki 之上加一层检索

## 一个被忽略的点

RAG 隐含的假设是"**原始文档本身就是最好的知识形态**"。
但真实材料往往是字幕、长文、播客转录 —— 你要的从来不是原文，
而是**被整理过、互相连着、能直接用的结论**。

LLM Wiki 干的就是这一步：**把"检索"换成"编译"**。
知识编译一次，之后只做维护。
