# 什么时候该给这个库加检索

> **本页来源**：一次查询。问题原话是
> 「我需要给这个库加向量检索吗？什么时候该加？」
> —— 回答被归档回 wiki，成为新页面。这正是 [[wiki/concepts/LLM Wiki]] 里
> 「好答案要归档回 wiki」那条。**提问本身也在生产知识。**

## 结论

**现在不需要。** 到大约 **100 个来源 / 数百个页面**之前，`index.md` 这个纯文本目录就够了 ——
回答问题时先读索引 → 定位相关页 → 深入读，实测"出奇地好用"，
**完全不需要向量库 / embedding / 检索调优那一套基础设施**。

## 为什么索引文件能撑这么久

关键在于**索引是人（LLM）维护的、带一句话摘要的目录**，
而不是一份需要机器算相似度的原始文本堆。

- 每个页面已经被加工过、有明确标题和一句话摘要 → 目录本身就是高质量的语义地图
- 条目按类别组织（来源 / 概念 / 实体 / 工具 / 综述）→ 查的时候是"按抽屉找"，不是"全库扫"
- 这和 RAG 的根本差别在于：RAG 要在一堆**未加工**的文本里找相似度，
  而这里是在一堆**已被加工**的摘要里找相关性 —— **后者的难度低一个量级**

## 什么时候该加

出现下面任意一种情况，再考虑上搜索引擎：

| 信号 | 说明 |
|---|---|
| 页面数进入数百量级 | 索引文件开始变长到"读一遍也费劲" |
| 同一个词在库里有很多不同含义 | 纯目录无法做歧义消解 |
| 需要跨页面找"我到底在哪里看过这件事" | 关键词匹配开始漏 |
| 想按时间/来源/标签做复杂过滤 | 该上 Dataview 或专门工具了 |

## 加什么

Karpathy 点名的方案是 [`qmd`](https://github.com/tobi/qmd)：

- 本地 markdown 搜索引擎
- **BM25 + 向量混合检索 + LLM 重排**，全部在设备上跑
- 同时提供 **CLI**（LLM 可以 shell out 调它）和 **MCP server**（LLM 可以当原生工具用）

**注意它是在 wiki 之上加一层检索，不是替换 wiki。** 这一点很重要 ——
真正让答案变好的不是检索，是**摄入时那一步的编译**。

## 换句话说

检索解决的是"**东西太多找不到**"。
而 [[wiki/concepts/LLM Wiki]] 解决的是"**东西根本没被整理过**"。

**先解决后者。前者可以等。**
